## 1. 基线算法的定义

### 1.1 算法身份

本文基线属于 **Extreme Point-based constructive heuristic**（极值点构造式启发式），由三个可独立指认的组件构成：

| 组件 | 内容 | 出处 |
|---|---|---|
| 装载策略 | **First-Fit**：按候选点顺序尝试，第一个可行位置即落子 | Johnson 等 1974（FFD 最坏情况界，*SIAM J. Comput.* 3(4):299–325） |
| 候选点 | **Extreme Points**：每个已放置货物的外表面角点 | Crainic, Perboli & Tadei 2008（*INFORMS J. Comput.* 20(3):368–384） |
| 加速结构 | **三维占用栅格**（整格占用，非连续几何） | Heßler, Hintsch & Wienkamp 2025（*EJOR* 327(3):820–837） |
| 排序 | 体积降序（主）、高度降序、底面积降序 | Bischoff & Marriott 1990（*EJOR* 44(2):267–276） |

### 1.2 与文献实现的差异（必须声明）

**本文基线不是任何单篇论文的忠实复现，而是上述三个组件的组合。** 逐项差异：

| 项 | Crainic 2008 原文 | 本文实现 |
|---|---|---|
| 候选点生成 | 六向正交投影，动态生成，数量随装载增长 | **固定 7 个角点**（底面 3 + 顶面 4） |
| 选点策略 | merit function 评估所有候选，选最优 | **first-fit，第一个可行即落子** |
| 排序 | 按高度/底面积/体积分簇 | 单一体积降序 |
| 目标 | 单容器装载率最大 | 单容器（校准）+ 多容器车辆数最小（本题） |

> 放弃 merit function 不是简化失误：Heßler 等（2025, *EJOR*）明确说明他们出于速度考虑同样放弃 merit function、改用 first-fit。本文基线与该文同构。
>
> 但**候选点只有 7 个角点**这一条是本文的简化。第 4 节给出三种点生成策略的对照，说明在本问题的算例上这一简化不构成瓶颈。

### 1.3 伪代码

```
输入：货物集合 I，容器规格 (L, W, H_cap)，高度余隙 δ
输出：容器列表 T，未装集合 R

T ← [], R ← []
E ← {(0,0,0)}                       # 极值点集
for it in sort(I, key = -体积):      # 体积降序
    placed ← False
    for t in T:                      # 首次适应：先试已有容器
        placed ← TryPlace(t, it)
        if placed: break
    if not placed:
        t ← NewContainer()
        placed ← TryPlace(t, it)
        if placed: T.append(t)
    if not placed: R.append(it)
return T, R

TryPlace(t, it):
    for p in sort(E, key = (z, y, x)):        # 最低、最靠后、最靠左优先
        for o in Orientations(it):            # 题面：定向件仅 1 种，其余最多 6 种
            if Feasible(t, p, o):             # 10 条约束逐条判定
                put(it, p, o)
                E ← E ∪ Corners7(p, o)        # 新增 7 个角点
                return True
    return False
```

`Feasible` 内部按 `src/constraints.py` 的 10 条约束逐条判定；校验时另有一份**独立实现**从解出发重新复核（见 `docs/01` 第 4 节）。

## 2. 外部校准：OR-Library `thpack1`

### 2.1 为什么必须做这件事

自造算例上得到的任何数字，都无法回答一个问题：**你的实现本身有没有写错？**

如果实现偏弱，「改进后车辆数从 2 降到 1」可能只是从一个差的起点往前挪了一步，而非真正的结构改进。校准的作用是给实现水平一个外部参照。

### 2.2 算例来源

| 项 | 内容 |
|---|---|
| 数据集 | **OR-Library `thpack1`–`thpack9`**（Brunel University, J.E. Beasley 维护） |
| 原始文献 | Bischoff & Ratcliff 1995（*EJOR* 84(1):68–84），3D 容器装载标准算例 |
| `thpack1` 规模 | **100 个算例** |
| 容器尺寸 | **587 × 233 × 220 cm**（20 ft 标准柜内尺寸） |
| 数据格式 | 每类货物给出三维尺寸 + 三个 0/1 标记，指示该方向是否允许竖放 |
| 许可 | 公开免费下载，学术使用 |

> **格式里的 0/1 标记就是「定向约束」的国际标准写法。** 本文题面的「定向件仅允许一种姿态」不是人为设定，而是该数据集的标准字段。

### 2.3 校准口径

| 项 | 取值 | 说明 |
|---|---|---|
| 容器数 | **1**（硬性） | `thpack` 为单容器问题；允许开多容器会把指标算错（见 §5.1 的踩坑记录） |
| 姿态 | 按数据 0/1 标记生成 | 与文献口径一致 |
| 指标 | **ISD = 装入体积 ÷ 容器容积** | 文献通用指标 |
| 约束 | 仅几何（不重叠、不越界、支撑）| 标准算例无易碎/定向/承重约束 |
| 排序 | 体积降序 | — |
| 硬件 | 单核 CPU，无 GPU | — |

### 2.4 结果

**100 个算例全部跑完，总耗时 235 秒。**

| 统计量 | 数值 |
|---|---|
| **平均 ISD** | **81.9%** |
| 中位数 | 82.4% |
| 最高 | 92.1% |
| 最低 | 67.3% |
| 标准差 | 4.8 pp |
| 单算例耗时 | 平均 **2.35 秒**，中位 1.75 秒 |
| 算例规模 | 69 – 476 件（中位 133） |

分布：

| ISD 区间 | 算例数 |
|---|---|
| 65%–70% | 3 |
| 70%–75% | 7 |
| 75%–80% | 21 |
| **80%–85%** | **41** |
| 85%–90% | 25 |
| 90% 以上 | 3 |

### 2.5 与文献水平的对比

| 方法 | 平均 ISD | 计算预算 | 代码可得 |
|---|---|---|---|
| Guesser, Alves De Queiroz & Miyazawa 2026（*EJOR* 333(2):337–348） | **95.91%**（1600 算例） | 30 秒 | ✅ MIT，C++ |
| 3dpack.ing 第三方引擎（190 个 Bischoff–Ratcliff 算例） | 92.40% | 41 秒（中位） | ❌ 商业 |
| Wang & Wang 2026（ICCNEA，EP + 遗传退火） | 89.73% | 未报 | ❌ |
| **本文基线（EP + first-fit + 7 角点）** | **81.9%**（100 算例） | **2.35 秒** | ✅ 本仓库 |

**差距 8.7–14.9 个百分点。** 对差距的解释必须区分两件事：

| 差距来源 | 证据 | 是否属于实现错误 |
|---|---|---|
| **计算预算** | 本文 2.35 秒 vs 文献 30 秒，相差 **12.8 倍** | 否，属设计取舍 |
| **搜索策略** | 文献用 beam search + maximal empty space 表示；本文是单轮贪心 | 否，属算法层级差异 |
| **候选点密度** | 本文 7 个角点 vs 文献六向动态投影 | 见 §4，本问题算例上影响不显著 |

**结论：81.9% 落在合理区间，说明实现可用；但它是「弱基线」，不是「SOTA 水平的实现」。** 报告中不得表述为「复现了 Guesser 2026」或「达到文献水平」。

## 3. 机制对照：哪些文献机制真的有用

为了判断差距来源，逐项实现候选机制并在同一批算例上对照。

> 口径说明：本节数据用 `clearance=3`（题面的顶部余隙）测得，与 §2 的 `clearance=0` 相差约 0.8 pp。
> **这个差异不改变任何排序结论**；本节读数应用于「机制之间谁更好」的比较，不要与 §2 的绝对值混用。

### 3.1 候选点生成策略

三种策略，其余全部固定（体积降序、first-fit、单容器）：

| 策略 | 候选点内容 | 点数/箱 |
|---|---|---|
| `corner7` | 底面 3 角 + 顶面 4 角 | 7 |
| `face3` | 三个正方向面心 + 角点 | 4 |
| `topgrid` | 顶面按相邻箱体边界切分成网格，再逐点三轴贴紧 | 4–16 |

实测（`thpack1` 算例 1–3）：

| 算例 | `corner7` | `face3` | `topgrid` |
|---|---|---|---|
| 1（112 件） | **85.2%** | 85.2% | 81.6% |
| 2（138 件） | 91.0% | 91.0% | 91.0% |
| 3（127 件） | 83.5% | 83.5% | 83.5% |
| 耗时（算例 1） | 1.6 s | 1.7 s | 3.1 s |

**两个结论：**

1. **`face3` 与 `corner7` 结果完全相同** —— 三轴贴紧投影会把面点推回到角点，两者等价。这解释了为什么「六向投影」在本实现里没有增量。
2. **`topgrid` 反而更差且更慢** —— 顶面网格点数量多，按 `(z, y, x)` 排序后优先填入低处小缝隙，**小件填缝阻塞了大件落位**。这是贪心策略的典型短视。

> 这条负面结论有方法论价值：**「候选点越多越好」在贪心框架下不成立。** 点数增加只在配合 beam search 或 merit function 时才转化为收益。

### 3.2 随机贪心多轮重启（RGS）

实现：对体积降序的排序键乘以 `U(1−α, 1+α)`（α = 0.25）后重排，重复 n 轮，取最优。

实测（`thpack1` 算例 1）：

| 配置 | 最好 ISD | 未装件数 |
|---|---|---|
| 体积降序（单轮） | 84.4% | 27 |
| 高度降序 | 84.4% | 27 |
| 底面积降序 | 82.5% | 12 |
| **随机化 20 轮取最优** | **84.4%**（与单轮相同） | 27 |

**RGS 在本实现上零增益。** 原因：极值点贪心是确定性的，随机化排序只改变「先装谁」，而候选点集完全由已放箱体的角点决定——**装载结构的骨架不变**，换序只在同一骨架里换填充顺序。

这也解释了文献中 RGS 有效的前提：那里的候选点密度高、搜索空间大，随机化才能探索到不同骨架。**RGS 不是独立有效的机制，它依赖底层候选点的表达能力。**

### 3.3 机制对照小结

| 机制 | 文献报告的增益 | 本文实测 | 判断 |
|---|---|---|---|
| 六向投影（等价于贴紧） | 提升缝隙利用 | **0**（贴紧后退化回角点） | 与 7 角点等价 |
| 顶面网格加密 | — | **−3.6 pp**（算例 1） | 贪心下有害 |
| RGS 多轮重启 | 主要性能来源 | **0**（20 轮） | 依赖候选点密度，此处不成立 |

**因此本文基线的「弱」不是可以靠加两个廉价机制补上的。** 要接近文献水平，需要更换搜索框架（beam search / maximal empty space），这超出本文范围，列入第 7 节局限。

## 4. 约束代价的量化（核心结果）

### 4.1 方法：约束层级递进

**这是本文最主要的实证结果，也是它区别于「把题解一遍」的地方。**

做法不是「一次移除一条」，而是**从最简的刚体层面开始，一级一级加约束**，看性能在哪一级断开。这比反向移除更能说明「约束的加入顺序是否重要」。

| 层级 | 内容 | 新增的约束 |
|---|---|---|
| **L0 刚体** | 只保证几何合法 | 不重叠、不越界、不超载重 |
| **L1 +支撑** | 加入力学要求 | 不得悬空（底面至少 1 格接触） |
| **L2 +易碎** | 加入易碎件规则 | 100% 贴合、只能落在标准件顶面、自身不承重 |
| **L3 +定向** | 加入定向件规则 | 单一姿态、上层重心不得超出其顶面投影 |
| **L4 +承重** | 加入面压限制 | 500 kg/m² |

每层是上一层的超集，其余一切固定（同一实现、同一排序、同一候选点策略）。代码见 `experiments/ablation_levels.py`，层级定义在 `src/pack_lib.py` 的 `LEVEL_*` 常量。

### 4.2 结果

**车型 2**（41.65 m³，700 元/趟；货物 28.735 m³，需 69.0% 装载率才能 1 辆装完）：

| 层级 | 车辆数 | 首车装载率 | 总成本 | 未装 | 断点 |
|---|---|---|---|---|---|
| L0 刚体 | **1** | 69.0% | **700 元** | 0 | — |
| L1 +支撑 | 1 | 69.0% | 700 元 | 0 | 无影响 |
| **L2 +易碎** | **2** | **59.9%** | **1400 元** | 0 | **← 唯一断点** |
| L3 +定向 | 2 | 59.9% | 1400 元 | 0 | 无影响 |
| L4 +承重 | 2 | 59.9% | 1400 元 | 0 | 无影响 |

**车型 1**（19.40 m³，450 元/趟；下界 2 辆）：

| 层级 | 车辆数 | 首车装载率 | 总成本 | 断点 |
|---|---|---|---|---|
| L0 刚体 | **2**（= 下界） | 89.3% | 900 元 | — |
| L1 +支撑 | 2 | 89.3% | 900 元 | 无影响 |
| **L2 +易碎** | **3** | 88.2% | 1350 元 | **← 唯一断点** |
| L3 +定向 | 3 | 86.2% | 1350 元 | 车辆数不变，装载率 −2.0 pp |
| L4 +承重 | 3 | 86.2% | 1350 元 | 无影响 |

### 4.3 结论

**① 断点唯一，且两种车型落在同一层。**

| 车型 | 刚体层面 | 全约束 | 代价 |
|---|---|---|---|
| 车型 2 | 1 辆（= 下界） | 2 辆 | **成本 ×2**（700 → 1400 元） |
| 车型 1 | 2 辆（= 下界） | 3 辆 | **成本 ×1.5**（900 → 1350 元） |

**在纯几何层面，两种车型都能达到下界。加入「易碎件单层」这一条后，两者同时退化到下界 +1。** 这是本文最凝练的一句话。

**② L1（不得悬空）零影响。**

说明在这个算例上，不考虑支撑也不会得到「浮空」的解——货物的尺寸分布使得贪心落点自然都有支撑。这条约束写成代码是为了正确性，但在本数据上不构成瓶颈。

**③ L3（定向）在车型 2 上零影响，在车型 1 上有 −2.0 pp 的装载率影响，但不改变车辆数。**

原因：90 件定向件的最长边本就是天然竖直方向，放开姿态反而让算法把箱子「躺平」以塞进缝隙，占用更多底面积。车型 1 空间更紧，这个效应才显现。

> 「零影响」与「小幅负影响」都值得报告：**知道哪条约束不起作用，与知道哪条起作用同样重要**——它决定优化该往哪里使劲。题面用两条约束描述定向件，但在给定数据上它们不是瓶颈。

**④ L4（承重）零影响，与解析计算一致。**

货物平均密度 143 kg/m³，堆满 247 cm 时理论最大面压约 353 kg/m²，低于 500 的上限。**这条在题面里占了不小篇幅，但在真实数据下从不触发。**

### 4.4 这个结论为什么可信

| 质疑 | 回答 |
|---|---|
| 「59.9% 是不是你的算法太弱？」 | 同一实现在标准算例上平均 81.9%、最高 92.1%（§2）。59.9% 显著低于自身水平，说明瓶颈在约束而非实现。 |
| 「换成更好的算法会不会就装得下？」 | 可能，但受限的是**结构**：易碎件要求底面 100% 贴合且只能落在标准件顶面。§4.5 的解析计算给出与算法无关的下界。 |
| 「L0 的解物理上合法吗？」 | 不一定——L0 允许悬空，它只是几何基准，不代表可执行的装车方案。L4 的解才是可执行解，且经独立校验器复核 0 违规。 |
| 「层级顺序会不会影响结论？」 | 会，所以层级按「几何 → 力学 → 类型特化 → 压力」的物理依赖排列，每一层只加不与前层冲突的约束。§4.3 ② 说明了 L1 零影响，意味着 L0 与 L1 的区别不影响后续归因。 |

### 4.5 与结构计算的一致性

解析计算（已形式化进 `lean/Boxpack.lean`）：

> 若 30 件易碎件全部置于底面，其底面积 10.50 m² 占车厢底面 63.0%，其上 207 cm 高度不可用，则
> 可用容积 = 41.650 − 10.50 × 2.07 = **19.91 m³ < 28.735 m³** → 一辆装不完。

Lean 定理 `fragile_on_floor_infeasible` 与 `fragile_on_top_feasible` 分别验证了「置底不可行」与「置顶不构成结构障碍」（`decide` 直接判定，不依赖 Mathlib）。

**实测 L1 为 1 辆、L2 为 2 辆，与解析计算方向一致**：约束的全部代价来自易碎件的垂直位置自由度被压缩。

## 5. 复现方式与踩坑记录

### 5.1 一个会毁掉全部结论的口径错误

首次校准跑出 **99.5%**，高于文献最好的 95.91%。

原因：`thpack1` 是**单容器**问题，而求解器默认允许多容器。算例 1 实际用了 **2 辆车**（85 + 27 件），但 ISD 只除以 **1 个容器**的体积 → 指标虚高。

**修正**：`max_trucks = 1`，并追加独立检查（越界 + 重叠），确认 0 违规后数字才落到 84.4%。

> 这件事记录在此，因为它说明：**指标口径错误比算法错误更危险**——算法错了会跑出难看的结果，口径错了会跑出好看的结果，而好看的结果没人会去查。

### 5.2 复现命令

```bash
# 标准算例校准（100 个算例，约 4 分钟）
py -3.12 experiments/bench_thpack.py

# 约束层级递进（车型2；车型1 传 --truck 0）
py -3.12 experiments/ablation_levels.py --truck 1

# 约束违规触发测试（12/12 应通过）
py -3.12 experiments/test_constraints.py
```

结果分别写入 `experiments/results/thpack1_m0.json` 与 `ablation_levels.json`。

算例文件随仓库提供（`data/thpack/thpack1.txt`，9 KB，公开数据）。若需重新下载：

```bash
curl -L -o data/thpack/thpack1.txt \
  https://people.brunel.ac.uk/~mastjjb/jeb/orlib/files/thpack1.txt
```

## 7. 建模完成之后：参数区间的优化路线

> 完整数学建模（`docs/03`）一旦定稿，问题就不再是「怎么解这一道题」，而是
> **「在哪些参数区间里，什么样的策略更好」**。这是后续工作的主体。

### 7.1 为什么必须转向区间

单点结论的弱点：**换一组数据就可能翻盘。** 附件 1 只有一组货、两种车型，从它得到的任何结论都无法回答「换一批货还成立吗」。

区间扫描把单点结论变成**带适用范围的结论**，这才构成可发表的实证研究。

### 7.2 五个待扫描的维度

| 维度 | 取值 | 要回答的问题 | 现有依据 |
|---|---|---|---|
| **易碎件占比** | 0% / 5% / 10% / 20% / 30% | 代价是线性的还是阶跃的？阈值在哪？ | L2 断点已定位（§4.3），但只有 30 件（10%）这一个点 |
| **定向件占比** | 0% / 10% / 30% / 50% | 到什么比例才真正影响车辆数？ | L3 在车型 2 零影响、车型 1 −2 pp（§4.3 ③） |
| **件数规模** | 100 / 300 / 600 | 约束代价是否随规模放大？ | 标准算例 69–476 件的 ISD 分布可作参照（§2.4） |
| **容器尺寸** | 车型 1 / 车型 2 / 混合 | 两种车型的最优组合区间在哪？ | 单车型结果已有（§4.2），混合未做 |
| **承重上限** | 300 / 500 / 800 kg/m² | 阈值降到多少才成为瓶颈？ | 500 时不触发（§4.3 ④），需找拐点 |

**优先级：易碎占比 > 件数规模 > 承重上限 > 定向占比 > 容器组合。** 理由：前两项直接决定核心结论的适用范围，后三项更可能是「无影响」的确认性实验。

### 7.3 每个区间的产出形态

区间的产出不是表格，是**相图**：横轴参数、纵轴车辆数（或相对下界的差距）、颜色表示约束代价。图上会出现清晰的分界线，这条线就是结论。

以易碎占比为例，预期形态：

```
相对下界的差距
   +2 ┤                    ╱─────
   +1 ┤          ╱────────╱
    0 ┼─────────╱
      └────┬────┬────┬────┬────→ 易碎件占比
           5%  10%  20%  30%
                ↑
            已测点（断点）
```

**如果曲线是阶跃的**（在某个占比突然跳变），说明存在结构阈值，可写成「易碎占比超过 X% 时，单层约束使车辆数必然增加」。
**如果是线性的**，说明代价可预测，可给出经验公式。
**两种结果都是有价值的结论**，不存在「跑出来不好看」的情况——这正是区间扫描相对于单点实验的优势。

### 7.4 与「优化」的关系

老师说「剩下就是不同区间的不同优化」，这包含两层：

| 层 | 含义 | 本项目的对应 |
|---|---|---|
| **参数区间 → 策略选择** | 不同区间用不同算法/参数 | 例如低易碎占比时用 EP 即可，高占比时必须分层 |
| **参数区间 → 代价预测** | 给定参数就能预估车辆数与成本 | 从相图读出经验公式，用于实际排车 |

第二层是更实用的落点：**如果能在不跑算法的情况下，从货物参数直接估算需要几辆车，这就是一个可交付的工具。** 相图就是它的查找表。

### 7.5 现状与缺口

| 项 | 状态 |
|---|---|
| 单点结论（附件 1，两种车型，五个层级） | ✅ 已完成（§4） |
| 标准算例校准 | ✅ 已完成（§2，100 算例） |
| 区间扫描脚本（参数化算例生成器） | ⬜ 未写 |
| 相图（五个维度） | ⬜ 未做 |

**这是 N3 的任务。** 有了 §4 的单点结论和 §2 的外部校准，区间扫描才是可信的；反过来，如果先做扫描再校准，所有点都可能建立在错误的实现上。

## 8. 局限（必须写进报告）

1. **基线是弱基线，非 SOTA 实现。** 81.9% vs 文献 95.91%，差距主要来自搜索框架（beam search / maximal empty space），本文未实现。
2. **未跑通 Guesser 2026 的官方代码。** 该实现为 C++，需 gcc 14 + boost 1.83 + Docker，本机无 C++ 工具链。因此「与 SOTA 的差距」用的是文献报告值，不是同机同批对照。
3. **约束代价的量化只在一个算例上完成。** 附件 1 是唯一的真实算例；参数化算例族（易碎占比 5%/10%/20%/30%）尚未跑，无法给出代价随参数变化的曲线。
4. **`topgrid` 的负面结论只测了 3 个算例。** 样本偏小，不宜作为一般性结论，只能作为「本实现在本批算例上的观察」。
5. **未做小规模精确解对照。** MILP 在 15–20 件规模上的最优值尚未求解，因此「启发式距最优多远」仍然未知。
